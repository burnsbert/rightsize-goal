# Rightsize Goal

Handle a small request directly or run a persistent goal with a small engineering team. Choose the lowest-cost path likely to complete the user's objective. Delegate substantial work to suitable agents. Fable is break-glass: use it only after documented Opus struggle, and never otherwise. A persistent run keeps going until an independent validator confirms the goal is met, the user pauses it, or a limit is reached.

Discussing, reviewing, or installing this workflow is not itself a request to run a persistent goal. For a persistent run, resolve a working Python 3.11+ interpreter (`python3`, `python`, or `py -3.11`) and use it consistently for the examples below. Resolve the helper scripts relative to this installed skill directory, not the working project.

## Choose the execution path first

Before resolving agent names, reading accounting history, setting a session goal, initializing a gate, or dispatching an agent, judge the entire request. If it is one short, self-contained answer or action that the main session can complete and verify promptly, do it here and finish. A current-time lookup, a simple calculation, or a trivial localized edit with a proportionate check fits this path. Use the appropriate live tool when the answer depends on current or external facts. Do not call the Agent tool, set a session goal, create goal state or gate state, run the accounting helper, or manufacture subtasks for this path. The skill's explicit invocation alone does not require a persistent goal.

Use the persistent workflow below when the request has substantial investigation or implementation, independent work packages, meaningful rework risk, or explicit continuation requirements. A user-specified `/goal`, time or iteration bound, request to resume an existing run, or an active session goal for this objective also takes this path even if the immediate step is small; honor its saved state and bounds. If a direct task grows beyond the small-task test, move to the persistent workflow for the remaining work without repeating completed steps. If uncertain whether delegation pays off for a short coherent task, handle it in the main session and verify it proportionately.

## Resolve role names for a persistent run

The five roles ship either as a plugin or as user-level agent files, and the two install methods produce different dispatch names:

- Plugin install: `rightsize-goal:rightsize-junior-doer`, and so on for each role.
- Manual install into `~/.claude/agents/`: the bare name, `rightsize-junior-doer`.

For a persistent run, before the first dispatch, read the available-agents list for this session and record which form is present. Use that exact string as `subagent_type`. A bare name fails with "Agent type not found" under a plugin install. Record the resolved prefix in goal state and reuse it.

If a persistent run needs an agent and none of the roles is available, say so plainly and stop rather than substituting a default agent: the roles exist to pin model and effort, and the Agent tool has no dispatch-time effort override.

## Cost and completion

Optimize expected total spend to reach the user's acceptance conditions, including worker effort, context transfer, coordination, verification, and likely rework. Successful goal completion remains the objective. Do not weaken acceptance to save money, and do not buy expensive reassurance when adequate evidence already exists.

Two levers move cost on this host, and they are not equally strong:

- **Model tier.** Haiku, Sonnet, Opus, and Fable are ordered from cheapest to most expensive per token. Use that ordering as your planning prior. The exact published rates are in [references/tariff.json](references/tariff.json); read them there rather than inventing numbers or percentages. The spread from cheapest to most expensive is roughly tenfold, so moving one tier down saves less here than the tier names suggest, and a single rework cycle can erase it.
- **Effort.** Every tier except the Haiku junior pins an effort level, and effort drives how many tokens a model spends at a fixed rate. Claude Code's session default is `xhigh`; no role here runs above `high`. The Sonnet 5 and Fable 5.1 roles run at their documented API default of `high`. Opus 5.5's API default is `medium`, and the senior role deliberately runs one level above it at `high`, so the Opus struggle that opens the Fable gate reflects a serious attempt.

Do not invent numeric effectiveness ratings, relative-cost percentages, or effort multipliers. Use the accounting helper's measured token usage and versioned tariff calculations to learn actual task cost patterns, with calculated amounts explicitly labeled. Choose by task fit and revise routing from observed acceptance, rework, escalation, and usage.

- Before dispatch, briefly judge the task's uncertainty, consequence of error, and cheapest tier likely to succeed. Record the routing reason in the existing assignment row, not as a separate planning exercise. Do not mechanically send every task through every tier.
- When capability is uncertain and a failed attempt would be cheap and reversible, give the cheaper plausible worker a bounded task with a clear checkpoint. If the task is already hard or likely to stretch that tier, assign Opus directly. A cheap attempt is useful only when it can advance the work or reveal something that changes the next assignment.
- Buy expensive effort for the difficult portion. When practical, let a cheap tier gather precise evidence or execute an understood plan and let Opus resolve the hard question. Use Fable only under the escalation gate below. Keep related simple operations together, but do not give one worker the whole goal merely to avoid handoffs.
- Every dispatch carries a fixed overhead: the worker's system prompt and skill context are billed as cache-write tokens before it reads a single project file. Bundle closely related small work rather than creating one agent per shell command or file edit.
- At meaningful results or checkpoints, reassess fit: continue with a worker making useful progress, move up when evidence shows a capability mismatch, and move down when the remaining work becomes routine. Do not interrupt a productive assignment solely to switch tiers; normally change ownership at a clean handoff. Neither past spending nor an idle expensive agent justifies more expensive work.
- Use observed success, rework, and escalation patterns to tune later assignments in this project. Record concise routing adjustments in goal state, linked to supporting task IDs. Preserve the model roster, user constraints, and the Fable gate; do not silently rewrite roles or claim broad capability conclusions from one result.
- After every completed, failed, cancelled, or interrupted assignment, capture its result and cost evidence before choosing the next worker. Record the exact per-assignment token categories the accounting helper reports. If usage is not attributable to that assignment, record `usage/cost=unavailable`; do not allocate a session aggregate across tasks, infer usage from elapsed time or visible output, or substitute a benchmark average.
- Label the measurement surface. A price calculation from token counts is an `API-equivalent estimate`, not the user's actual Claude bill, and a Claude Code subscription is not billed per token at all. Record the tariff version and the input, cache-read, cache-write, and output categories used in any calculation. Output tokens already include thinking tokens; never add thinking a second time.
- At each checkpoint, compare the measured usage with the result: accepted, rework required, unresolved but informative, or wasted. Adjust later routing only when the evidence is comparable and the change still respects capability and the Fable gate. Never invent a numeric savings claim when attribution is incomplete.

## Start and resume

For a persistent run, read [references/accounting.md](references/accounting.md) at start and at resume. Use its helper for assignment accounting and inspect the current directory's `.rightsize-goal/usage.sqlite3` report before the first dispatch. After every terminal assignment, capture usage, judge the result, and read the updated local report before choosing the next worker. No Rightsize Goal run ledger or log is written to the user configuration directory.

Follow the lightweight-coordinator boundary below whatever model the main session runs. Running a capable model at the top does not make it the default executor.

- Capture the user's objective, acceptance evidence, constraints, and any explicit budget. Calling this workflow with an objective authorizes creating a session goal; discussing or installing the workflow does not.
- Inspect the current session goal. If a goal is already active and matches this objective, reuse it. Never clear or overwrite an unrelated active goal to make room; if it conflicts, resolve which goal the user intends before continuing.
- Choose how the run persists, and record the choice in goal state. Under a plugin install (role names carry the `rightsize-goal:` prefix), the plugin's Stop hook provides persistence: run the self-driving loop described under [Self-driving persistence](#self-driving-persistence) and do not propose `/goal`. If a Claude Code session goal for this objective is already active, for example because the user started with `/goal Use the rightsize-goal skill to ...`, let it drive and start the drive state with `--mode host_goal` so the plugin hook stands down. Under a manual install there is no plugin hook, so set a session goal: prefer the `ProposeGoal` tool when it is available in this session, which renders a one-keypress approval without blocking your work. If it is unavailable and `/goal` can be used, give the user a ready-to-paste command beginning `/goal Use the rightsize-goal skill to ...`; carry over the actual objective, observable acceptance conditions, and material constraints. Do not give only a bare condition that omits the skill or ask the user to put a second slash command inside `/goal`. If `/goal` is unavailable because of workspace trust or hook settings, explain that and continue the authorized work in the current session with saved state. Do not claim a goal or a hook is holding the session when it is not.
- A Claude Code session goal is a session-scoped Stop hook: it blocks the session from stopping until a separate evaluator confirms the condition, and it clears itself when the condition is met. It is not cross-session scheduling. If the user needs work to resume in a later session, point at the saved goal state and gate, or at `/loop` and `/schedule` if the user wants to arrange recurrence themselves. Never promise unattended continuation the host does not provide.
- The coordinator needs enough judgment to route, verify, and decide acceptance; it does not need to be a specific model. Opus at `medium` effort is a good default. Sonnet 5 at `high` or above is also a capable coordinator, and either is a reasonable choice. Haiku is not suitable for this role. A skill's frontmatter can only override model and effort for one turn, so this skill does not change them; the user sets them with `/model` and `/effort`. Read the actual coordinator effort from the `CLAUDE_EFFORT` environment variable and the actual coordinator model from the session transcript, and record both, or `unknown`. Note the pairing once in the log and move on; do not repeatedly flag a capable coordinator as a mismatch, and never falsely label the model.
- In the current directory, create `.rightsize-goal/` and allocate a unique filename-safe goal ID from a system-local timestamp plus random suffix. Never reuse or overwrite an existing ID. Keep `.rightsize-goal/<goal-id>.jsonl` as that goal's call/result log, `.rightsize-goal/<goal-id>.state.json` as its current state, `.rightsize-goal/<goal-id>.gate.json` as its completion gate, and `.rightsize-goal/<goal-id>.drive.json` as its goal text, task list, verdicts, and status. Announce the goal ID and log path. For Git projects, add `.rightsize-goal/` to the local Git exclude file if needed; do not commit project run data.
- On continuation or compaction, read that goal's state, log, gate, drive state (`drive.py show`), and current session goal state; reconcile live children and outputs, then resume without repeating finished assignments. Recover by goal ID or session goal identity; otherwise match active records by exact objective and resolve ambiguity with the user. A running child remains live; only a runtime-confirmed interrupted or failed child is treated as interrupted. Do not reset failure history or budgets.

## Self-driving persistence

A skill cannot start `/goal`, so under a plugin install the plugin ships a Stop hook that plays that role. At every stop it runs `drive.py hook`. It stays silent unless this session owns an active self-driving goal in the current directory, and it keeps the session working until the validator returns DONE for the current goal, the goal is paused or waiting on the user, or a limit is reached. Its continuation message names what is unmet and the open tasks. Treat it as your next instruction: re-read the drive state, update the task list, and dispatch. Do not argue with it or end the turn with nothing done. If no progress is recorded across several continuations, it lets the session stop and tells the user, so record progress honestly rather than to silence it. Pressing Esc always interrupts, because Stop hooks do not run on user interrupts.

Use [scripts/drive.py](scripts/drive.py) after `goal_gate.py init`. `start` and `resume` bind the goal to the current session through `CLAUDE_CODE_SESSION_ID`, so run them from the main session. A session owns at most one active goal: if either command refuses because another goal is active here, ask the user which goal they intend, then pause or finish the other one first. Keep the drive state under a host goal or a manual install too: it holds the goal text, amendments, task list, and verdicts either way.

```text
python3 <skill-dir>/scripts/drive.py start --drive .rightsize-goal/<goal-id>.drive.json --gate .rightsize-goal/<goal-id>.gate.json --goal "<the user's goal, verbatim>" [--mode host_goal]
python3 <skill-dir>/scripts/drive.py task --drive <drive> --id T001 --title "<outcome>" --owner <role> --why "<what it serves>"
python3 <skill-dir>/scripts/drive.py task --drive <drive> --id T001 --status done
python3 <skill-dir>/scripts/drive.py progress --drive <drive> --note "<what changed>"
python3 <skill-dir>/scripts/drive.py amend --drive <drive> --user-words "<the user's words>" --goal "<the full reworded goal>"
python3 <skill-dir>/scripts/drive.py verdict --drive <drive> --verdict NOT_DONE --reason "<reason>" --reason "<reason>" --validator <agent-id>
python3 <skill-dir>/scripts/drive.py verdict --drive <drive> --verdict DONE --reason "<summary>" --evidence <saved-receipt> --validator <agent-id>
python3 <skill-dir>/scripts/drive.py status --drive <drive> --set paused --reason "<the user's words>"
python3 <skill-dir>/scripts/drive.py resume --drive <drive>
python3 <skill-dir>/scripts/drive.py show --drive <drive>
```

- **The goal text.** Record the user's goal verbatim at start; it stays the test of done. When the user calls an audible, such as changing scope, adding or removing a requirement, or redirecting priorities, record their words and the full reworded goal with `amend`, then re-plan. If an instruction is ambiguous, ask rather than guess. An amendment makes any earlier DONE verdict stale.
- **The task list.** Keep the living task list in the drive state: add tasks as you discover them, update their status as they move, and split, merge, or drop them as evidence changes. Mark a task `in_progress` when you dispatch it and move it on when its result arrives: while any task is `in_progress`, the hook lets you end the turn to wait for workers, and their completion notification wakes you. Record `progress` after each accepted, reworked, or informative result. The hook builds its continuation message from this list, so keep it current.
- **Only through `drive.py`.** Never edit the drive file by hand. The hook's continuation message repeats the exact commands with full paths.
- **Validation.** When you believe the goal is met, dispatch `rightsize-validator` with the current goal text, the original text and any amendments, the acceptance conditions, the working directory, and where to look. Do not include your argument that the goal is met. Account for the dispatch like any other assignment. Save its receipt under `.rightsize-goal/` and record the verdict with `verdict`, citing the receipt as DONE evidence. On NOT_DONE, turn every reason into tasks with `--source validator` and continue. If `verdict` reports `repeated_reasons`, the last approach did not work: change the hypothesis or route that task to a stronger tier instead of retrying the same thing. Any recorded work after a DONE verdict makes it stale, so finish task updates before validating.
- **Finishing.** After a fresh DONE and a `completion_eligible` gate check, record `status --set complete` and give the final report.
- **Pause and resume.** When the user says stop, pause, or anything that clearly means it, checkpoint running workers and record `status --set paused --reason "<their words>"`; the hook then lets the session end. When you need the user's input and no independent work remains, record `status --set waiting_on_user` with the question as the reason. When the user says resume, or clearly means it, run `resume`, which reactivates the goal and binds it to the current session, then continue from the saved state. If it is unclear whether the user wants to pause, ask.
- **Limits.** When the gate reports `limit_reached`, the hook asks once for an incomplete handoff. Give it, then record `status --set incomplete` with the limit as the reason.

## Lightweight coordinator

The top-level session is the manager, not the default senior engineer. Delegate substantive engineering work to the lowest capable doer, including `rightsize-senior-doer` for hard work. Retain prioritization, assignment, acceptance decisions, escalation, and goal ownership at the top level. Do not routinely combine manager and implementer responsibilities simply because the manager also runs a capable model.

- For a persistent run, dispatch suitable routine exploration or implementation to a cheap tier. Do not solve the task yourself first and then ask a cheap worker to transcribe the solution. Read required project and skill instructions yourself; delegate optional code inspection, precise evidence collection, routine plan details, edits, test execution, and log analysis within the cheap tiers' capability.
- Give `rightsize-midlevel-doer` ownership of a coherent basic work package: inspect the relevant code, choose an approach using established patterns, implement, verify, and return a receipt. Supply outcome, boundaries, and acceptance criteria rather than a line-by-line plan. `rightsize-junior-doer` receives explicit smaller tasks with examples. Known hard work still goes directly to Opus; discovery of hard work triggers a handoff rather than repeated retries at a cheap tier.
- Keep coordinator turns focused on dispatch, a decision based on evidence, integration, or goal-state bookkeeping. Do not expand a brief routing decision into a second investigation or re-plan an accepted work package at every checkpoint. Read full worker artifacts or raw logs only when acceptance, risk, inconsistency, or a specific unresolved question warrants it.
- Ask for compact worker receipts: outcome, changed paths, checks and results, unresolved issues, and next useful action. Keep detailed logs in artifacts and pass focused context to workers. Reuse an appropriate worker for related tasks, and bundle related operations instead of creating one child per shell command or file edit.
- Verify proportionately without duplicating the work. The coordinator judges whether the evidence meets acceptance; routine execution of checks can stay with a cheap tier. Use an independent check where warranted by risk, not a paid review ritual for every trivial change. Run the deterministic gate directly; do not ask a model to recalculate time or iteration arithmetic.
- Subagents run in the background and notify you when they finish. If only workers are running and there is no useful coordinator action, wait for that notification. Do not fill the interval with speculative planning, repeated reasoning, or status polling. Never fabricate or predict a pending agent's result.
- Before substantive execution in the main session, open a task with `agent=main` and record why a cheaper worker is unsuitable (hard reasoning, a consequential decision, or a genuinely smaller total cost than another handoff). Tiny checks and bookkeeping may remain local without a separate task. Main-session implementation and research must be visible in the same goal log as child assignments.
- At a meaningful milestone, inspect whether routine work drifted into the main session and adjust the next assignments. Summaries should distinguish coordinator decisions from main-session execution, and flag duplicated investigations or excessive handoffs. Use actual model and token usage when available; task counts or short visible replies do not prove low reasoning-token spend. Do not enforce a percentage quota that would push genuinely hard work onto a cheap tier.

These instructions reduce avoidable coordinator work but cannot cap the main model's internal reasoning or per-turn charges. Keep model and effort as the user selected them; do not claim the skill can switch them for the session. Evaluate coordinated runs against unassisted runs using observed usage, acceptance, and rework before claiming savings.

## Persistent completion gate

Recognize `--minimum-time="30 minutes"` and `--maximum-time="3 hours"` anywhere in the invocation that reached this skill, whichever command form was used (`/rightsize-goal:rightsize-goal` under a plugin install, `/rightsize-goal` otherwise). These are skill arguments, not `/goal` flags. Forward their values unchanged to the helper's `init` command; do not merely remember them in prose or round them into estimated hours. Supported values are one nonnegative number plus seconds, minutes, hours, or days (also `s`, `m`, `h`, `d` and common abbreviations); fractional values such as `1.5 hours` are accepted. An omitted flag supplies no bound. Reject invalid units, contradictory bounds, or conflicting prose and flag instructions before dispatch. The helper retains legacy `--min-hours` and `--max-hours`, but combining an old and a new flag for the same bound is rejected.

After initialization, read back the persisted `not_before` and `deadline` timestamps, convert them to the computer's local timezone, announce those bounds in readable local date and time with AM/PM, and link the state file. Keep UTC only in machine gate state for reliable arithmetic; do not require the user to convert UTC when reading logs or progress updates. The minimum is a mandatory completion condition and the maximum a mandatory dispatch ceiling at checkpoints. Do not override, shorten, or reset either to declare success. Resume uses those saved bounds; changed flags require explicit user steering and a recorded change, not an unnoticed replacement of the state file.

For every new run, use [scripts/goal_gate.py](scripts/goal_gate.py) to create `.rightsize-goal/<goal-id>.gate.json` beside the goal log. Python 3.11+ is supported. Resolve the script relative to this installed skill. The coordinator alone writes this state through the helper. On resume use the existing file; never initialize a new clock or zero the iteration count to recover. If a pre-existing run has no gate, recover the start and completed work from trustworthy evidence before adding bounds; do not invent historical credit or silently apply new defaults.

Capture user-specified minimum and maximum time and iterations separately. Do not invent mandatory minimums or a maximum budget when none was requested. For "at least six hours or twenty iterations, whichever is longer," require BOTH six elapsed hours AND twenty completed iterations. A maximum on either dimension is a ceiling, not success. Reject same-dimension maximums below minimums; explain that a maximum can end the run incomplete before other minimums are met.

The helper measures elapsed wall-clock hours from its saved UTC start, NOT active labor, model compute, or billed time. If the user specifically requires active working hours excluding pauses, explain that this helper cannot verify those and resolve that measurement requirement rather than relabeling elapsed hours as work. Never sleep, busy-poll, repeat unchanged checks, or manufacture tasks just to meet a minimum. Continue meaningful authorized experiments, improvements, or verification; if none are possible, preserve the unmet requirements and report the concrete dependency.

Example commands (bounds are illustrative, never defaults):

```text
python3 <skill-dir>/scripts/goal_gate.py init --state <run-id>.gate.json --objective "<objective>" --minimum-time="30 minutes" --maximum-time="3 hours" --min-iterations 20 --max-iterations 30
python3 <skill-dir>/scripts/goal_gate.py iteration --state <run-id>.gate.json --id I001 --hypothesis "<testable idea>" --action "<meaningful action>" --result "<evaluated result>" --evidence <existing-evidence-path>
python3 <skill-dir>/scripts/goal_gate.py check --state <run-id>.gate.json
```

Define a substantive iteration for the task before starting: one hypothesis or improvement, a meaningful action or experiment, an evaluation, and retained evidence. Count it only after evaluation; a failure can count when it adds evidence. Child messages, individual tool calls, cosmetic variations, waiting, and unchanged retries are not separate iterations. Multiple workers contributing to one experiment count as one iteration. The helper validates IDs and the existence of evidence paths; the coordinator must judge substance and evidence quality.

Run `check` on resume, after each completed iteration, before dispatching another work batch, and immediately before a completion claim. Pass `--acceptance-met` ONLY after `rightsize-validator` has returned DONE for the current goal and work and you recorded it with `drive.py verdict`, so `drive.py show` reports `acceptance_fresh: true`. Until that flag is justified, the helper must not report completion eligibility. Record the latest decision, elapsed hours, completed iterations, unmet conditions, and next action in current state.

- `completion_eligible` (exit 0): acceptance and every minimum are met. Reconcile all live children and required deliverables, then record and report verified completion from the gate and goal state. A worker finishing its bounded assignment never completes the parent goal by itself. Record `drive.py status --set complete`. An active session goal clears itself once its evaluator agrees; do not tell the user to run `/goal clear` after success.
- `continue` (exit 2): do not claim completion or conclude with a discretionary handoff while useful authorized work remains. Dispatch the next useful assignment or inspect a running one. When a route stalls, use the evidence-based Opus and Fable escalation process instead of treating exhausted ideas as task success.
- `limit_reached` (exit 3): stop dispatching new work, arrange safe checkpoints for running workers, preserve results, and report `incomplete: limit reached` with unmet criteria, then record `drive.py status --set incomplete`. Under a host goal, tell the user they can end it early with `/goal clear`; do not attempt to satisfy the goal condition by asserting it is met. Bounds are checked at checkpoints, so an in-flight operation may overrun; give workers remaining budget and a practical stop condition before dispatch.
- Invalid, missing, or corrupt gate state is a verification problem, never permission to complete. Recover from evidence or report the dependency.

An explicit user stop, pause, or cancel overrides `continue`: stop new dispatches, safely checkpoint or interrupt workers, persist state, record `drive.py status --set paused`, and report where the goal stands and how to resume. A gate does not override user steering.

This is a deterministic completion check invoked by the workflow, not a tool interceptor or an external watchdog. A model can still fail to call it, and usage limits, crashes, or interruptions can end execution. Never promise uninterrupted wall time. Keep session-goal status and gate status distinct in the log.

## Assignment routing

| Tier | Model / effort | Assign when |
| --- | --- | --- |
| Main session (manager) | A capable model; Opus / medium or Sonnet 5 / high are both good choices | Own priorities, goal state, routing, acceptance decisions, and escalation. Delegate engineering execution to the cheapest capable doer; keep tiny coordination and checks local when dispatch costs more. |
| `rightsize-junior-doer` (entry-level to junior engineer) | Haiku 4.5 (no effort control) | Very basic, explicit tasks with an existing example or prescribed approach: straightforward localized edits, precise lookups, known-pattern updates, and routine checks with clear acceptance criteria. Its context window is smaller than the other tiers, so keep the working set small. |
| `rightsize-midlevel-doer` (midlevel engineer) | Sonnet 5 / high | Independently execute bounded work using established patterns, including moderately complex work needing more judgment: small features or fixes, several related edits, straightforward code tracing, routine implementation choices without step-by-step instructions, multi-file changes in established architecture, localized debugging across known components, and focused research synthesis. |
| `rightsize-senior-doer` (senior engineer) | Opus 5.5 / high | Hard work beyond bounded midlevel scope: deeply ambiguous debugging, unfamiliar complex integrations, substantive research, consequential design tradeoffs, difficult new hypotheses, or deep interacting constraints. No cheaper failure is required first. |
| `rightsize-principal-doer` (principal engineer / lead architect) | Fable 5.1 / high | Break-glass only: the hardest bounded unresolved implementation, reasoning, or fresh-direction consultation after documented Opus struggle. Never assigned otherwise. |
| `rightsize-validator` (independent validator) | Opus 5.5 / high, read-only | Only when the coordinator believes the goal is met: judge the current goal from its own evidence and return DONE or NOT DONE with reasons tied to the goal. It does no implementation and is not a routine reviewer. |

These experience levels are task-assignment analogies, not claims about model credentials. Keep tiny tasks in the main session when dispatch would add more overhead than value. For useful basic delegation, give `rightsize-junior-doer` explicit guidance and examples; use `rightsize-midlevel-doer` when a developer can independently choose routine details within established patterns, including moderately complex work needing more judgment. Neither is the route for hard tasks. If the junior tier exposes only modest additional complexity, the midlevel tier may help; if either discovers hard or ambiguous work, route the evidence directly to Opus without requiring another cheap attempt. A Haiku or Sonnet failure alone never qualifies for Fable.

Use `implement`, `research`, or `brainstorm` as the assignment mode for any tier, within that tier's complexity boundary. Separate mode instructions preserve research-only boundaries without duplicating the model roster. Research returns cited evidence and uncertainty. Brainstorming returns a few materially different, grounded hypotheses with a cheap discriminating next step; novelty must advance the objective, not merely sound exciting.

Treat struggle as evidence: a substantive approach failed its acceptance check and Opus can explain why the next step is unresolved, or Opus examined the relevant evidence but can produce only already-tried or unsupported directions. A typo, a transient tool failure, a waiting job, an absent credential, or a missing user decision is not a reasoning failure. Restored access is new evidence that can justify retrying the same technical approach.

The required evidence normally comes from a dispatched Opus-tier child, not from the coordinator's own work: give `rightsize-senior-doer` the bounded hard task, then relay its documented struggle. The coordinator assembles that package and may add what it noticed afterward, including evidence from cheaper agents that sharpens the unresolved question. What it may not do is manufacture the qualifying struggle out of cheaper material: a Haiku or Sonnet worker's failure remains insufficient on its own, however it is relayed. A coordinator that itself runs Opus may count its own logged substantive investigation or brainstorming attempt, but that is the exception rather than the normal route, and merely reading a failed cheap-tier receipt never qualifies. Fable is expensive; treat reaching it as something to justify, not something to arrange.

Use principal Fable/high when senior Opus/high has documented genuine struggle on the bounded hard task and the unresolved core needs a bounded expert perspective, architecture decision, implementation, or discriminating hypothesis. Log why the role and effort are the smallest sufficient purchase. After two substantive failed approaches without new evidence, stop repeating that route and change tier or hypothesis.

Before each Fable assignment, log the linked Opus assignments, attempts and results, the remaining question, why Fable is justified, and a bounded deliverable and stop condition. Default to one Fable assignment at a time and one consultation per unresolved question; another needs new evidence and a recorded reason. Fable may implement when that bounded implementation itself is the unresolved hard core after Opus struggle. Never use Fable for routine review, polling, clerical edits, or automatic final signoff. After the hard uncertainty is resolved, return implementation and verification to the lowest capable tier. Worker agents cannot spawn agents and must not escalate themselves; the main coordinator dispatches according to this workflow.

If the account cannot use one of these models, the affected roles will fail at dispatch. Disclose the limitation, treat the highest available tier as the top of the ladder, and say in the final report that escalation was capped. Never silently substitute a different model into a role name, because the ledger and the tariff both key on the model actually served.

## Execute and verify

- Task the goal out the way a capable development team would. Picture how a tech lead would break this goal into tickets for real engineers: what each ticket would say, where one engineer's work naturally hands off to another's, what gets tested or reviewed on its own, and which pieces are routine enough for a junior versus which need a senior. Use that picture to choose task boundaries and owners, then revise it as evidence arrives.
- Before dispatch, identify the next few meaningful pieces of the goal and choose a task boundary at which new evidence could change the next step. Keep this a short, revisable view of work, not a speculative full-project backlog. After each result or material discovery, add, split, merge, reorder, or drop remaining tasks as warranted; do not execute an obsolete breakdown just because it was written down.
- Make each assignment manageable for its owner: one coherent outcome, clear scope, a useful stop or handoff point, and checks the coordinator can assess. Split work when it crosses substantial uncertainty, distinct implementation and evaluation stages, different required skills or ownership, or a long-running operation whose result should guide the next step. For example, a generator change with focused tests can be one task; inspect the evidence before assigning a live evaluation and deciding whether another change is justified. Do not bundle discovery, design, implementation, live assessment, and next-round recommendations into one worker assignment by default.
- Keep a single assignment small enough to finish well within the retirement point. If `finish` reports that an assignment alone grew its context past it (`assignment_growth_tokens`), that work package was too large: split similar work into smaller assignments with their own checkpoints from then on.
- Task size is about coherence and verifiability, not the number of steps. A batch of many simple, repetitive operations can be one task when the method is known and the output has a clear check. Avoid both mammoth open-ended assignments and one child per command or file edit. Log meaningful main-session tasks too, but not every tool call.
- For every child assignment, send: task ID, mode, desired outcome and acceptance checks, relevant paths and evidence, owned files or read-only scope, forbidden changes, prior attempts, stop condition, and expected concise result. State that others share the codebase and that their edits must be preserved.
- Spawn the named role with the Agent tool, using the resolved `subagent_type` string. The role definition pins model and effort. The Agent tool's `model` parameter cannot set effort, so overriding the model on a generic agent does not reproduce a role; if a role is unavailable, report that limitation rather than silently substituting a different model or effort.
- Two dispatch modes exist and both are supported. Detect which one is live from what the Agent tool returns, and record it in goal state.
  - **Agent Teams enabled** (recommended). Passing `name` makes the worker a teammate: it runs as its own addressable session, `ListAgents` lists it, and `SendMessage` sends it follow-up assignments with its context intact. The tool returns `<agentName>@<teamName>`; record that string verbatim as the agent ID. Prefer this mode, because reusing a teammate for a natural follow-on task avoids paying to rebuild its context. A known Claude Code bug ([anthropics/claude-code#80569](https://github.com/anthropics/claude-code/issues/80569)) makes a teammate silently inherit the coordinator's own session effort instead of the role's pinned `effort`; `model` is unaffected. Check `/tasks` while the teammate is active to see its actual effort, and record it if it differs from the role's declared value; do not claim the role's effort was honored without checking.
  - **Agent Teams unavailable.** Omit `name` and dispatch a plain in-process subagent. The tool returns a bare agent id. This mode works fully, with one consequence: there is no `SendMessage` reuse, so a follow-up means a fresh worker that must be given its context again. Bundle related work more aggressively here while retaining manageable outcomes and evidence checkpoints, and say in the final report that reuse was unavailable.
- A teammate is a whole session, not a lightweight helper: it loads its own project instructions and does its own orientation before it reads a single file you named. Its floor cost per dispatch is therefore several times a plain subagent's. Bundle accordingly, and do not spawn a teammate for work that is smaller than its own startup cost.
- Give each spawned agent a new task ID per assignment and record the returned agent ID against it. Do not send cheaper work to an existing expensive agent just because it is idle.
- **Worker lifecycle.** Reuse a teammate when its context has room and the next task is a natural follow-on: fixing or extending its own work, the next step in the same pipeline, or an adjacent piece of the subsystem it just learned. Give work in an unrelated area to a fresh teammate with a short handoff, even when an idle teammate has the right role: a teammate re-reads everything it has seen on every request, so unrelated history costs tokens and invites stale instructions. `task_usage.py finish` reports the worker's `context_tokens` and a `context_advice` line that applies these bands: below 120,000 tokens there is room for a natural follow-on; from 120,000 to 200,000, reuse it only for a small follow-on that depends on what it already knows; at 200,000 or more, retire it. Shut down a teammate as soon as you judge it unlikely to get another assignment, because its area is finished, it is retired, or the remaining work belongs to other roles. To do that, send it a shutdown request with `SendMessage` (message `{"type": "shutdown_request", "reason": "<why>"}`) and record it in goal state. The user's invocation of this workflow is their request that you shut down teammates you no longer need, so originating these shutdown requests is authorized. Every role can accept one by replying with a shutdown response. If a teammate declines or cannot reply, record that and give it no more work. Keep live teammates few, typically three to five. Plain in-process subagents end when they finish and need no shutdown.
- A worker does not inherit your working directory. State the absolute working directory in the assignment whenever it differs from the session's, and have the worker confirm the paths it actually touched in its receipt.
- Check that the acceptance command actually exercises the work before trusting its result. A runner that collects nothing still exits successfully: `unittest discover` reports `NO TESTS RAN` for pytest-style bare functions, a filtered run can match zero cases, and a missing runner can send a worker to an improvised substitute. Confirm the check ran the expected number of cases, and treat a zero-case pass as a failed verification, not a pass. Where a named runner may be absent, say which fallback is acceptable and require the worker to report the command and its case count verbatim.
- The main session alone owns the goal state and assignment accounting. Integrate completed results, verify appropriate acceptance evidence, and finish each task with the coordinator's accepted, rework, unresolved, cancelled, or failed outcome. The helper writes the result line with tokens and estimated cost. An agent saying "done" is not completion evidence, and neither is a receipt that formats its own prose to look like runner output; require the literal command and its real output. Verification that itself stretches a cheap tier goes to Opus; avoid duplicating an entire investigation without cause.
- Preserve the user's authorization boundaries throughout persistence. A goal is not permission for unrelated external writes, messages, publishing, purchases, commits, pushes, or destructive operations.
- Keep advancing while useful authorized work remains and no explicit ceiling or user stop has been reached. Record a necessary user or external dependency and work on independent tasks meanwhile; if none remain, report the concrete dependency. Honor user stop and cancel steering.

## Goal state and log contract

Keep current objective, acceptance conditions, session goal identity, coordinator model/effort, explicit budget, resolved role prefix and dispatch mode, next action, live assignments, evidence paths, latest gate decision, and routing adjustments in `.rightsize-goal/<goal-id>.state.json`. Keep the goal text, amendments, the short revisable task list, verdicts, and pause status in the drive state through `drive.py`, not duplicated here. Update this state as work changes; it is not an event log or a fixed backlog. Keep the gate in `.rightsize-goal/<goal-id>.gate.json` and the project-local usage ledger in `.rightsize-goal/usage.sqlite3`.

The only Rightsize Goal log is `.rightsize-goal/<goal-id>.jsonl`. Every line is one JSON object with `event` equal to `agent_call` or `agent_result`, plus the goal ID, task ID, agent role, and timestamp. `task_usage.py start` writes the call line; `finish` writes the result line with the coordinator's outcome, measured token categories or an unavailable reason, and estimated USD cost or an unavailable reason. For a new child, invoke `start` immediately after dispatch with the exact returned agent ID; for a reused child, invoke it before the follow-up. If dispatch fails before `start`, write one `agent_call` and one `agent_result` line for that attempted task with the intended role, `outcome=failed`, and unavailable usage and cost. Never invent token counts or a price.

When a result is insufficient, start a new task ID with `--prior-task <old-task-id> --reason "<what failed and why another call is needed>"`. The helper rejects a linked call without a reason. Capture meaningful main-session tasks with `--main --role main` and close each with attributable usage when exposed. Put progress notes, routing decisions, gate checkpoints, and final tallies in the state file or user-facing report, never as extra log lines. Do not log secrets, full transcripts, or source code. On resume, preserve existing JSONL lines and ID; do not rewrite history or treat an idempotent `finish` as another result. In the final response, link the goal log, summarize accepted/rework outcomes and measured coverage, and report verified completion and any material limits.
