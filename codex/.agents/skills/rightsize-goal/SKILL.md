# Rightsize Goal

Handle a small request directly or run a persistent goal with a small engineering team. Choose the lowest-cost path likely to complete the user's objective. Delegate substantial work to suitable agents; reserve Astra for evidenced Sol difficulty.

Discussing, reviewing, or installing this workflow is not itself a request to run a persistent goal. For a persistent run, resolve a working Python 3.11+ interpreter (`python`, `python3`, or `py -3.11`) and use it consistently for the examples below. Resolve helpers relative to this installed skill. Installed role TOMLs are under `$CODEX_HOME/agents` (normally `~/.codex/agents`); when working from the distribution, they are under `codex/.codex/agents`.

## Choose the execution path first

Before reading accounting history, creating a native goal, initializing a gate, or dispatching an agent, judge the entire request. If it is one short, self-contained answer or action that the main thread can complete and verify promptly, do it here and finish. A current-time lookup, a simple calculation, or a trivial localized edit with a proportionate check fits this path. Use the appropriate live tool when the answer depends on current or external facts. Do not spawn agents, create goal state, run the accounting helper, or manufacture subtasks for this path. The skill's explicit invocation alone does not require a persistent goal.

Use the persistent workflow below when the request has substantial investigation or implementation, independent work packages, meaningful rework risk, or explicit continuation requirements. A user-specified `/goal`, time or iteration bound, or request to resume an existing run also takes this path even if the immediate step is small; honor its saved state and bounds. If a direct task grows beyond the small-task test, move to the persistent workflow for the remaining work without repeating completed steps. If uncertain whether delegation pays off for a short coherent task, handle it in the main thread and verify it proportionately.

## Cost and completion

Optimize expected total spend to reach the user's acceptance conditions, including worker effort, context transfer, coordination, verification, and likely rework. Successful goal completion remains the objective. Do not weaken acceptance to save money, or buy expensive reassurance when adequate evidence already exists. The user's operating assumption is that Luna-to-Sol and Sol-to-Astra are large cost jumps; use that qualitative ordering without inventing prices or treating elapsed time as a billing meter.

Use the qualitative ordering the user supplied as the initial planning prior: Luna is substantially cheaper than Sol, and Astra is substantially more expensive than Sol. Reasoning effort can also increase token use. Do not invent numeric effectiveness ratings, relative-cost percentages, or effort multipliers. Use the accounting helper's measured token usage and versioned tariff calculations to learn actual task cost patterns, with calculated amounts explicitly labeled. Choose by task fit and revise routing from observed acceptance, rework, escalation, and usage.

- Before dispatch, briefly judge the task's uncertainty, consequence of error, and cheapest tier likely to succeed. Record the routing reason in the `agent_call` line using `--reason`, without a separate planning exercise. Do not mechanically send every task through every tier.
- Classify the assignment before choosing a worker: basic factual/mechanical work goes to Luna/high; routine work using established patterns goes to Luna/xhigh; moderate and hard work goes to Sol/medium; the most complex and challenging work goes directly to Sol/high when failure would put Astra escalation materially at risk. Do not use a lower tier as a speculative trial for work already classified above it.
- When capability is uncertain and a failed attempt would be cheap and reversible, give the cheaper plausible worker a bounded task with a clear checkpoint. If the task is already hard or likely to stretch Luna, assign Sol directly. A cheap attempt is useful only when it can advance the work or reveal something that changes the next assignment.
- Buy expensive effort for the difficult portion. When practical, let Luna gather precise evidence or execute an understood plan and let Sol resolve the hard question. Use Astra only under the escalation gate below. Keep related simple operations together, but do not give one worker the whole goal merely to avoid handoffs.
- At meaningful results or checkpoints, reassess fit: continue with a worker making useful progress, move up when evidence shows a capability mismatch, and move down when the remaining work becomes routine. Do not interrupt a productive assignment solely to switch tiers; normally change ownership at a clean handoff. Neither past spending nor an idle expensive agent justifies more expensive work.
- Use observed success, rework, and escalation patterns to tune later assignments in this project. Record concise routing adjustments in goal state, linked to supporting task IDs. Preserve the model roster, user constraints, and Astra gate; do not silently rewrite roles or claim broad capability conclusions from one result.
- After every completed, failed, cancelled, or interrupted assignment, capture its result and cost evidence before choosing the next worker. Prefer an exact task-level charge or credits reported by Codex. If unavailable, record the exact task-level token categories exposed by the runtime. If neither is attributable to that assignment, record `usage/cost=unavailable`; do not allocate a session aggregate across tasks, infer usage from elapsed time or visible output, or substitute a benchmark average.
- Label the measurement surface: actual Codex credits/charge, API-billed usage, or token usage only. A price calculation from token counts is `API-equivalent estimate`, not the user's actual Codex bill, unless the billing surface explicitly says otherwise. Record the tariff/version and input, cached-input, cache-write, output/reasoning, and separately charged tool categories used in any calculation. Do not add reasoning twice when output already includes it.
- At each checkpoint, compare the measured bill or usage with the result: accepted, rework required, unresolved but informative, or wasted. Adjust later routing only when the evidence is comparable and the change still respects capability and the Astra gate. Never invent a numeric savings claim when attribution is incomplete.

## Start and resume

For a persistent run, read [references/accounting.md](references/accounting.md) at start/resume. Use its helper for assignment accounting and inspect the current directory's `.rightsize-goal/usage.sqlite3` report before the first dispatch. After every terminal assignment, capture usage, judge the result, and read the updated local report before choosing the next worker. No Rightsize Goal run ledger or log is written to the user configuration directory.

When the main session is Sol, follow the lightweight-coordinator boundary below. Choosing Sol for orchestration does not make it the default executor.

- Capture the user's objective, acceptance evidence, constraints, and any explicit budget. Calling this workflow with an objective authorizes creating that goal; discussing or installing the workflow does not.
- Inspect the native goal with `get_goal`. Reuse an existing matching goal; never overwrite or mark an unrelated unfinished goal complete to make room. If it conflicts, resolve which goal the user intends before creating another. If the tools cannot cancel/replace it, the user must resolve it through the product's supported controls, or explicitly choose current-session-only work on the new objective with saved goal state. Never misuse `blocked` as cancellation.
- Use `create_goal` for a new requested objective. Set `token_budget` only when the user explicitly supplied one. If native goal tools are unavailable, disclose that automatic goal continuation is unavailable; use saved goal state for continuity and continue within the current session without pretending a native goal exists.
- The intended top-level session is `gpt-6-sol` at medium, acting as the manager. It delegates engineering tasks to Luna/high (junior), Luna/xhigh (midlevel), Sol/medium (senior), and Sol/high (staff) as needed. Sol/high is the best first-pass worker for the most complex and challenging assignments, particularly when a weaker first attempt would increase the likelihood or cost of Astra escalation. Astra/medium is the principal engineer, reserved for the post-Sol escalation boundary below. The manager and `rightsize-senior-doer` use the same model/effort but have different responsibilities. A skill cannot change the running main model. Record the actual model/effort when known, otherwise `unknown`; disclose a mismatch once and continue under the manager boundary without changing global defaults or falsely labeling the model.
- In the current directory, create `.rightsize-goal/` and allocate a unique filename-safe goal ID from a system-local timestamp plus random suffix. Never reuse or overwrite an existing ID. Keep `.rightsize-goal/<goal-id>.jsonl` as that goal's call/result log, `.rightsize-goal/<goal-id>.state.json` as its current state, and `.rightsize-goal/<goal-id>.gate.json` as its completion gate. Announce the goal ID and log path. For Git projects, add `.rightsize-goal/` to the local Git exclude file if needed; do not commit project run data.
- On continuation or compaction, read that goal's state, log, gate, and native goal state; reconcile live children and outputs, then resume without repeating finished assignments. Recover by goal ID or native goal identity; otherwise match active records by exact objective and resolve ambiguity with the user. A running child remains live; only runtime-confirmed interrupted/failed children are treated as interrupted. Do not reset failure history or budgets.

## Lightweight Sol coordinator

The top-level Sol session is the manager, not the default senior engineer. Delegate substantive engineering work to the lowest capable doer, including `rightsize-senior-doer` or `rightsize-staff-doer` for hard work. Retain prioritization, assignment, acceptance decisions, escalation, and native goal ownership at the top level. Do not routinely combine manager and implementer responsibilities simply because the manager runs Sol too.

- For a persistent run, dispatch suitable routine exploration or implementation to Luna. Do not solve the task in Sol first and then ask Luna to transcribe the solution. Read required project/skill instructions yourself; delegate optional code inspection, precise evidence collection, routine plan details, edits, test execution, and log analysis within Luna's capability.
- Luna/high may do precise factual lookups with clear source requirements and no material judgment call. Luna/xhigh may gather and organize routine evidence using established criteria. Research requiring synthesis, interpretation, ambiguous source evaluation, or a consequential recommendation belongs to Sol.
- Give Luna/xhigh ownership of a coherent basic work package: inspect the relevant code, choose an approach using established patterns, implement, verify, and return a receipt. Supply outcome, boundaries, and acceptance criteria rather than a line-by-line plan. Luna/high receives explicit smaller tasks with examples. Known hard work still goes directly to Sol; discovery of hard work triggers a handoff rather than repeated Luna retries.
- Keep coordinator turns focused on dispatch, a decision based on evidence, integration, or goal-state bookkeeping. Do not expand a brief routing decision into a second investigation or re-plan an accepted work package at every checkpoint. Read full worker artifacts or raw logs only when acceptance, risk, inconsistency, or a specific unresolved question warrants it.
- Ask for compact worker receipts: outcome, changed paths, checks and results, unresolved issues, and next useful action. Keep detailed logs in artifacts and pass focused context to workers. Reuse appropriate worker context for related tasks, and bundle related operations instead of creating one child per shell command or file edit.
- Verify proportionately without duplicating the work. The coordinator judges whether the evidence meets acceptance; routine execution of checks can stay with Luna. Use an independent check where warranted by risk, not a paid review ritual for every trivial change. Run the deterministic gate directly; do not ask a model to recalculate time or iteration arithmetic.
- If only workers are running and there is no useful coordinator action, use the runtime's agent wait mechanism. Do not fill the interval with speculative planning, repeated reasoning, or frequent status polls. Honor user-facing update requirements without redoing analysis.
- Before substantive execution in the Sol main session, open a task with `agent=main` and record why Luna is unsuitable (hard reasoning, consequential decision, or a genuinely smaller total cost than another handoff). Tiny checks and bookkeeping may remain local without a separate task. Main-session implementation and research must be visible in the same goal log as child assignments.
- At a meaningful milestone, inspect whether routine work drifted into Sol and adjust the next assignments. Summaries should distinguish coordinator decisions from main-session execution, and flag duplicated investigations or excessive handoffs. Use actual model/token usage when available; task counts or short visible replies do not prove low reasoning-token spend. Do not enforce a percentage quota that would push genuinely hard work onto Luna.

These instructions reduce avoidable coordinator work but cannot cap the main model's internal reasoning or per-turn charges. Keep model/effort fixed as selected by the user; do not claim the skill can dynamically switch it. Evaluate Sol-coordinated runs against Luna-coordinated runs using observed usage, acceptance, and rework before claiming savings.

## Persistent completion gate

Recognize `--minimum-time="30 minutes"` and `--maximum-time="3 hours"` on a `$rightsize-goal` invocation (including one inside `/goal`). These are skill arguments, not native `/goal` flags. Forward their values unchanged to the helper's `init` command; do not merely remember them in prose or round them into estimated hours. Supported values are one nonnegative number plus seconds, minutes, hours, or days (also `s`, `m`, `h`, `d` and common abbreviations); fractional values such as `1.5 hours` are accepted. An omitted flag supplies no bound. Reject invalid units, contradictory bounds, or conflicting prose/flag instructions before dispatch. The helper retains legacy `--min-hours`/`--max-hours`, but combining an old and new flag for the same bound is rejected.

After initialization, read back the persisted `not_before` and `deadline` timestamps, convert them to the computer's local timezone, announce those bounds in readable local date/time with AM/PM, and link the state file. Keep UTC only in machine gate state for reliable arithmetic; do not require the user to convert UTC when reading logs or progress updates. The minimum is a mandatory completion condition and the maximum a mandatory dispatch ceiling at checkpoints. Do not override, shorten, or reset either to declare success. Resume uses those saved bounds; changed flags require explicit user steering and a recorded change, not an unnoticed replacement of the state file.

For every new run, use [scripts/goal_gate.py](scripts/goal_gate.py) to create `.rightsize-goal/<goal-id>.gate.json` beside the goal log. Python 3.11+ is supported. Resolve the script relative to this installed skill, not the working project. The coordinator alone writes this state through the helper. On resume use the existing file; never initialize a new clock or zero the iteration count to recover. If a pre-existing run has no gate, recover the start and completed work from trustworthy evidence before adding bounds; do not invent historical credit or silently apply new defaults.

Capture user-specified minimum and maximum hours/iterations separately. Do not invent mandatory minimums or a maximum budget when none was requested. For "at least six hours or twenty iterations, whichever is longer," require BOTH six elapsed hours AND twenty completed iterations. A maximum on either dimension is a ceiling, not success. Reject same-dimension maximums below minimums; explain that a maximum can end the run incomplete before other minimums are met.

The helper measures elapsed wall-clock hours from its saved UTC start, NOT active labor, model compute, or billed time. If the user specifically requires active working hours excluding pauses, explain that this helper cannot verify those and resolve that measurement requirement rather than relabeling elapsed hours as work. Never sleep, busy-poll, repeat unchanged checks, or manufacture tasks just to meet a minimum. Continue meaningful authorized experiments, improvements, or verification; if none are possible, preserve the unmet requirements and report the concrete dependency.

Example commands (bounds are illustrative, never defaults):

```text
python <skill-dir>/scripts/goal_gate.py init --state <run-id>.gate.json --objective "<objective>" --minimum-time="30 minutes" --maximum-time="3 hours" --min-iterations 20 --max-iterations 30
python <skill-dir>/scripts/goal_gate.py iteration --state <run-id>.gate.json --id I001 --hypothesis "<testable idea>" --action "<meaningful action>" --result "<evaluated result>" --evidence <existing-evidence-path>
python <skill-dir>/scripts/goal_gate.py check --state <run-id>.gate.json
```

Define a substantive iteration for the task before starting: one hypothesis or improvement, meaningful action/experiment, evaluation, and retained evidence. Count it only after evaluation; failure can count when it adds evidence. Child messages, individual tool calls, cosmetic variations, waiting, and unchanged retries are not separate iterations. Multiple workers contributing to one experiment count as one iteration. The helper validates IDs and evidence-path existence; the coordinator must judge substance and evidence quality.

Run `check` on resume, after each completed iteration, before dispatching another work batch, and immediately before a completion claim. Pass `--acceptance-met` ONLY after independently verifying the user's outcome criteria and recording their evidence in goal state. Until that flag is justified, the helper must not report completion eligibility. Record the latest decision, elapsed hours, completed iterations, unmet conditions, and next action in current state.

- `completion_eligible` (exit 0): acceptance and every minimum are met. Reconcile all live children and required deliverables; if a matching native goal exists, mark it complete. Otherwise record and report verified completion from the gate and goal state. A worker finishing its bounded assignment never completes the parent goal by itself.
- `continue` (exit 2): do not claim completion or conclude with a discretionary handoff while useful authorized work remains. Dispatch the next useful assignment or inspect a running one. When a route stalls, use the evidence-based Sol/Astra escalation process instead of treating exhausted ideas as task success.
- `limit_reached` (exit 3): stop dispatching new work, arrange safe checkpoints for running workers, preserve results, and report `incomplete: limit reached` with unmet criteria. Do not mark the native goal complete or misuse `blocked` to emulate pausing. Use the product's supported pause/limit control if available; if not, tell the user to pause the native goal. Bounds are checked at checkpoints, so an in-flight operation may overrun; give workers remaining budget and a practical stop condition before dispatch.
- Invalid/missing/corrupt gate state is a verification problem, never permission to complete. Recover from evidence or report the dependency.

An explicit user stop/cancel overrides `continue`: stop new dispatches, safely checkpoint or interrupt workers, persist state, and report stopped/incomplete using only supported product pause/cancel controls. A gate does not override user steering.

This is a deterministic completion check invoked by the workflow, not a native tool interceptor or external watchdog. A model can still fail to call it, and usage limits, crashes, or product pauses can interrupt execution. Never promise uninterrupted wall time. Strong enforcement requires a host-level supervisor that controls completion and continuation; that is outside this installed skill. Keep native goal status and gate status distinct in the log.

## Assignment routing

| Tier | Model / effort | Assign when |
| --- | --- | --- |
| Main session (manager) | `gpt-6-sol` / medium | Own priorities, goal state, routing, acceptance decisions, and escalation. Delegate engineering execution to the cheapest capable doer; keep tiny coordination/checks local when dispatch costs more. |
| `rightsize-junior-doer` (junior engineer) | `gpt-6-luna` / high | Very basic, explicit tasks with an existing example or prescribed approach: straightforward localized edits, factual research with clear sources and no judgment call, precise lookups, known-pattern updates, and routine checks with clear acceptance criteria. |
| `rightsize-midlevel-doer` (midlevel engineer) | `gpt-6-luna` / xhigh | Independently execute bounded work using established patterns: small features or fixes, several related edits, straightforward code tracing, routine implementation choices without step-by-step instructions, and gathering or organizing evidence using defined criteria. |
| `rightsize-senior-doer` (senior engineer) | `gpt-6-sol` / medium | Moderately complex or hard work beyond bounded midlevel scope: multi-file changes needing judgment, unfamiliar integrations, substantive research, consequential design tradeoffs, or difficult new hypotheses. No Luna failure is required. |
| `rightsize-staff-doer` (staff engineer) | `gpt-6-sol` / high | The most complex and challenging implementation, research, design, or debugging, and deep interacting constraints where more Sol effort is likely to pay off. Use as the strongest first pass when Astra escalation is a credible risk, or after Sol/medium stalls. |
| `rightsize-principal-doer` (principal engineer / lead architect) | `gpt-6-astra` / medium | Bounded unresolved expert implementation, reasoning, or fresh-direction consultation after documented Sol struggle. |

These experience levels are task-assignment analogies, not claims about model credentials. Keep tiny tasks in the main session when dispatch would add more overhead than value. For useful basic delegation, give `rightsize-junior-doer` explicit guidance and examples; use `rightsize-midlevel-doer` when a developer can independently choose routine details within established patterns. Neither is the route for hard tasks. If Luna/high exposes only modest additional complexity, Luna/xhigh may help; if either discovers hard or ambiguous work, route the evidence directly to Sol without requiring another Luna attempt. A Luna failure alone never qualifies for Astra.

Use Sol/medium directly for moderate work beyond Luna's established-pattern scope, including when Luna reveals that level of complexity. Do not send known moderate work to Luna merely because a failed attempt would be cheap. Known hard, deeply ambiguous, or consequential architectural work can go directly to senior or staff. A failed Luna attempt alone does not qualify for Astra; documented Sol struggle is still required.

Use `implement`, `research`, or `brainstorm` as the assignment mode for any paid tier, within that tier's complexity boundary. Separate mode instructions preserve research-only boundaries without duplicating the model roster. Research returns cited evidence and uncertainty. Brainstorming returns a few materially different, grounded hypotheses with a cheap discriminating next step; novelty must advance the objective, not merely sound exciting.

Treat struggle as evidence: a substantive approach failed its acceptance check and Sol can explain why the next step is unresolved, or Sol examined the relevant evidence but can produce only already-tried/unsupported directions. A typo, transient tool failure, waiting job, absent credential, or missing user decision is not a reasoning failure. Restored access is new evidence that can justify retrying the same technical approach.

When the main session is Sol, a logged substantive investigation or brainstorming attempt by that coordinator can supply the required Sol evidence. Merely reading a failed Luna receipt does not. Use Sol/medium for ordinary hard work. Use Sol/high directly for the most complex first-pass assignments, or when earlier evidence shows the problem has entered that tier. Neither is an obligatory extra consultation on every coordinator decision.

The Sol/high staff engineer is the preferred pre-Astra worker when the assignment is unusually complex, has deeply interacting constraints, or is likely to need Astra if the first approach fails. Route such work there directly instead of requiring a Sol/medium senior attempt. After senior Sol/medium struggles, prefer staff Sol/high when deeper analysis of the same evidence is promising, but staff is not a compulsory toll when the senior has already produced sufficient evidence that a bounded principal engineer escalation is needed. Use principal Astra/medium when the unresolved core needs a bounded expert perspective, architecture decision, implementation, or discriminating hypothesis. There is no Astra/low probe: reaching the Astra gate means buying enough reasoning budget for the principal assignment once. Log the linked Sol evidence, why Astra is the smallest sufficient purchase, and a bounded deliverable and stop condition. After two substantive failed approaches without new evidence, stop repeating that route and change tier or hypothesis.

Before each Astra assignment, log the linked Sol assignment(s), attempts/results, remaining question, why Astra is justified, and a bounded deliverable/stop condition. Default to one Astra assignment at a time and one consultation per unresolved question; another needs new evidence and a recorded reason. Astra may implement when that bounded implementation itself is the unresolved hard core after Sol struggle. Never use Astra for routine review, polling, clerical edits, or automatic final signoff. After the hard uncertainty is resolved, return implementation and verification to the lowest capable tier. Child/worker agents must not spawn agents or escalate themselves; the main coordinator dispatches according to this workflow.

## Execute and verify

- Before dispatch, identify the next few meaningful pieces of the goal and choose a task boundary at which new evidence could change the next step. Keep this a short, revisable view of work, not a speculative full-project backlog. After each result or material discovery, add, split, merge, reorder, or drop remaining tasks as warranted; do not execute an obsolete breakdown just because it was written down.
- Make each assignment manageable for its owner: one coherent outcome, clear scope, a useful stop or handoff point, and checks the coordinator can assess. Split work when it crosses substantial uncertainty, distinct implementation and evaluation stages, different required skills or ownership, or a long-running operation whose result should guide the next step. For example, a generator change with focused tests can be one task; inspect the evidence before assigning a live evaluation and deciding whether another change is justified. Do not bundle discovery, design, implementation, live assessment, and next-round recommendations into one worker assignment by default.
- Task size is about coherence and verifiability, not the number of steps. A batch of many simple, repetitive operations can be one task when the method is known and the output has a clear check. Avoid both mammoth open-ended assignments and one child per command or file edit. Log meaningful main-session tasks too, but not every tool call.
- For every child send: task ID, mode, desired outcome and acceptance checks, relevant paths/evidence, owned files or read-only scope, forbidden changes, prior attempts, stop condition, and expected concise result. State that others share the codebase and their edits must be preserved.
- Spawn the named role when available. Its file pins model and effort. If the role is not loaded but explicit model overrides are supported, read its TOML instructions and use a default agent with the exact model/effort and those instructions in the assignment. Use `fork_turns="none"` and supply focused context for such overrides; never use a full-history fork that rejects them. If neither route is available, report the limitation rather than silently substituting a different model or effort.
- Reuse an existing suitable agent for related follow-ups; give each new assignment a new task ID and record the reused agent ID. Do not send cheaper work to an existing expensive agent just because it is idle. Parallelize only independent assignments with distinct ownership and useful coordinator work; respect the runtime's concurrency limits and serialized resources such as GPU queues.
- The main session alone owns the goal state and assignment accounting. Integrate completed results, verify appropriate acceptance evidence, and finish each task with the coordinator's accepted, rework, unresolved, cancelled, or failed outcome. The helper writes the result line with tokens and estimated cost. An agent saying "done" is not completion evidence. Verification that itself stretches Luna goes to Sol; avoid duplicating an entire investigation without cause.
- Preserve the user's authorization boundaries throughout persistence. A goal is not permission for unrelated external writes, messages, publishing, purchases, or destructive operations.
- Keep advancing while useful authorized work remains and no explicit ceiling or user stop has been reached. Close the native goal with `update_goal(status="complete")` only after the persistent completion gate returns `completion_eligible` and all required work is verified. For blocking and budget behavior, follow the live goal tool contract exactly: in particular, do not mark blocked after a single failed turn or complete merely because budget is low. Record a necessary user/external dependency and work on independent tasks meanwhile; if none remain, report the concrete dependency. Honor user stop/cancel steering.

## Goal state and log contract

Keep current objective, acceptance conditions, native goal identity, coordinator model/effort, explicit budget, next action, a short revisable view of pending tasks and their checkpoints, live assignments, evidence paths, and latest gate decision in `.rightsize-goal/<goal-id>.state.json`. Update this state as work changes; it is not an event log or a fixed backlog. Keep the gate in `.rightsize-goal/<goal-id>.gate.json` and the project-local usage ledger in `.rightsize-goal/usage.sqlite3`.

The only log is `.rightsize-goal/<goal-id>.jsonl`. Every line is one JSON object with `event` equal to `agent_call` or `agent_result`, plus the goal ID, task ID, agent role, and timestamp. `task_usage.py start` writes the call line; `finish` writes the result line with the coordinator's outcome, measured token categories or an unavailable reason, and estimated USD cost or an unavailable reason. For a new child, invoke `start` immediately after spawn with the exact returned thread ID; for a reused child, invoke it before the follow-up. If a dispatch fails before `start`, write one `agent_call` and one `agent_result` line for that attempted task with the intended role, `outcome=failed`, and unavailable usage and cost. Never invent token counts or a price.

When a result is insufficient, start a new task ID with `--prior-task <old-task-id> --reason "<what failed and why another call is needed>"`. The helper rejects a linked call without a reason. Put progress notes, routing decisions, gate checkpoints, and final tallies in the state file or user-facing report, never as extra log lines. Do not log secrets, full transcripts, or source code. On resume, preserve the existing JSONL lines and ID; do not rewrite history or treat an idempotent `finish` as another result. In the final response, link the goal log, summarize accepted/rework outcomes and measured coverage, and report verified completion and any material limits. If a native token-budgeted goal completes, include the final token usage returned by the goal tool.
